# 21｜後台內容與 Repo 漂移審計（API 覆蓋問題）

**日期：** 2026-09-21
**觸發原因：** CI build 的出街前閘門攔到 25 項錯誤，但本機 build 全部通過。
**結論：** 這不是閘門誤報，而是揭發了一個**架構級的內容漂移問題**——Repo 內已修正的內容，一直被正式後台的舊版本靜默覆蓋。

---

## 1. 為何本機通過、CI 失敗

`lib/data-resolver.ts` 的合併規則（檔案內有註明）：

```
同 slug → API（後台）版本覆蓋本地版本，並保留原本位置
```

- **本機 build：** 連不到後台 API（無 `ADMIN_API_KEY`），`fetchBlogPosts()` 回 `null`，直接使用 `lib/blogData.ts` 的乾淨 fallback。
- **CI build：** GitHub Actions 帶有 `ADMIN_API_KEY` secret，成功拉取後台資料，並以其**覆蓋**本地版本。

因此**過去在 repo 內對文章文案所做的修正，只要後台有同 slug 的舊版本，就從未真正上到正式站。**

這是本次審計最重要的發現：閘門本身沒有問題，它只是在 CI 這個「唯一能看見後台資料」的環境裡，第一次把真象照出來。

---

## 3. 兩層修正

### 3.1 程式層（治本，不改後台資料）

新增 `lib/seo-title.ts`，提供 `stripBrandSuffix()` / `normalizeSeoTitle()`，並在
`lib/data-resolver.ts` 的 API 映射階段套用：

- 後台 blog `title` → 正規化
- 後台 portfolio `seoTitle` → 正規化

**為何在程式層修而非改後台 16 筆資料：**

1. 這是**顯示邏輯**問題，不是資料錯誤。同一個標題在 template 之下應該只輸出一次品牌名。
2. 修在資料層之後，編輯人員日後**連尾綴一齊輸入、抑或唔輸入，輸出都會正確**，不需要靠人記住格式。
3. 不需要改動 16 筆正式後台資料。

正規化會**重複執行**直至無尾綴為止，可處理歷史上已疊加兩次的情況。
支援半形／全形直線、有無 `Agency`、大小寫差異。

**驗證：** 用後台 16 個真實 `seo_title` 作 fixture 測試，全部輸出單一尾綴且 ≤62 字（0/16 失敗）；
邊界測試（雙尾綴、`｜` 全形、`| ADWire` 無 Agency、大小寫、空字串）全部正確。

## 4. 閘門規則修正

Build 首次執行時另攔到 5 個**假警報**：Article 19 使用「保證排名」，但全部屬否定語境。

三項修正（詳見 `deliverables/20`）：

1. **對稱窗口**（前後各 60 字）——Google 官方句式「…保證能排名第一位，建議您另請高明」的否定詞在**後**，舊規則只看前方。
2. **中文引號內放行**——被「」包住代表作者在討論該說法。
3. **只認多字否定詞**——移除裸「不」「無」，它們曾造成**假陰性**（真違規漏檢）。

新增 `--selftest`（已接上 `postbuild`）：4 項必須攔截 + 7 項必須放行，
**任何調整若令真違規漏檢，build 直接失敗**。

## 5. 建議（未執行，待負責人決定）

1. **後台 `seo_title` 欄位應加輸入提示或前端驗證**，說明品牌尾綴由系統自動加上，不需要自行輸入。程式層的正規化已可防禦，但源頭改善可避免編輯困惑。
2. **考慮在後台加標題長度提示**（連尾綴 62 字），避免超長標題上線後被 Google 截斷。
3. **審視資料來源優先次序。** 現行「後台覆蓋 repo」的設計，會令 repo 內經審核的文案修正無法生效。若 repo 是文案的審核來源，應考慮改為「repo 為準、後台只作新增」，或建立明確的同步流程。
4. **本機 build 看不到後台內容**，這是閘門的最大盲點。建議在 CI 的閘門步驟之外，另設一個只讀取後台資料的定期檢查，令漂移可以及早發現，而不是等到部署時才被攔截。
